Official Origami Python bindings: what breaks, and the fix we plan to ship

A plan to publish an rocm-origami wheel that is built against the ROCm SDK's shared liborigami — not one that embeds its own copy — so two incompatible Origami builds can no longer land in one Python process and corrupt memory. This follows the sanctioned rocSHMEM wheel pattern (rocm-systems #9471, merged; TheRock #5638, open).

Phase 2 complete Build-against-installed Follows rocSHMEM Linux-first No code changed yet

1The one-sentence version

Read this if you read nothing else.

Origami ships a C++ selection engine and a Python extension that wraps it. Today, when someone installs the Python package from PyPI, the build compiles Origami's C++ statically into the extension. The extension carries its own private copy of Origami. If a process also loads the ROCm SDK's separate shared liborigami (directly, or through a neighbor like PyTorch or hipBLASLt), two different Origami builds now coexist in one address space. When their internal data structures disagree on size, one copy writes past what the other allocated, and the process crashes.

The fix, in one line

Stop compiling Origami into the extension. Build the extension against the installed liborigami via find_package(origami), so it dynamically depends on the one SDK copy and there is nothing to duplicate. The wheel ships no Origami of its own.

This is not a bespoke design — it is an existing ROCm pattern

rocSHMEM already did exactly this: rocm-systems #9471 (merged) moved its binding to a standalone project that builds against an installed rocSHMEM via find_package, and TheRock #5638 (open) builds that wheel in TheRock's Python-packages CI lane. Origami fits the pattern more cleanly — it already ships a shared liborigami and is host-only, so it needs none of rocSHMEM's device-code (--offload-arch) machinery. And Origami's build is already half-wired for it: python/CMakeLists.txt has the find_package(origami) branch today, just defaulted off.

What is verified vs. what is not

Verified: the static embed (observed by readelf), and that the struct problem_t grew by 16 bytes when two fields (num_cus, q_heads) were added — a local recompile measured it at 80 → 96 bytes.

Not verified: the ticket's headline "112 → 128 bytes" figure did not reproduce, and the internal issue ROCM-29472 is inaccessible, so the exact PyTorch-CI causal chain stays unproven. The fix does not depend on the exact byte counts — removing the second copy removes the failure class regardless.

3Why the obvious fixes were rejected

Three plausible-sounding directions were checked against primary sources and adversarially re-verified. All three were refuted. Recording them here so they are not re-attempted.

Tempting ideaWhy it fails
Just turn ORIGAMI_ENABLE_PYTHON=ON in TheRock's component build. TheRock PR #6425 deliberately dismantled per-component binding builds; the component build ships only the native library. The binding is built in a separate lane instead — TheRock's Python-packages workflow, which builds the wheel against the installed library (this is the mechanism section 5 uses, and what rocSHMEM #5638 wires up).

5How the fix works

The fix has three moving parts. At build time the extension links the installed library, so it carries a real dependency and no copy of its own. The build lane supplies that installed library. At run time, the SDK's copy is the only Origami to resolve.

Why this removes the crash

The crash needs two Origami copies with different problem_t layouts in one process. Building against the installed shared library means the wheel contains zero Origami of its own — so divergence is impossible by construction, not merely deduplicated after the fact. The extension links a stable SONAME, so a co-loaded consumer (hipBLASLt, PyTorch) resolves to the same object. One layout, one allocation contract, no out-of-bounds write.

Why not force-shared + bundle a copy?

An earlier interim plan kept building Origami from source, forced it shared (-DORIGAMI_BUILD_SHARED_LIBS=ON), bundled a liborigami.so.1 in the wheel, and relied on preload order to deduplicate against the SDK copy. It was chosen only to avoid needing the SDK library at build time. That reimplements, more weakly, what find_package(origami) gives directly — and it keeps an Origami copy in the wheel that can drift from the SDK. Once the build lane supplies the installed library (exactly what TheRock's Python-packages workflow does), the reason to bundle disappears, so the plan drops it.

6The experiment that unblocked the plan

One observation gates three findings at once (the loader contract, the incident root cause, and the Python-version tag). It was run, not assumed.

A wheel was built via the real pip / scikit-build-core standalone path inside rocm/dev-ubuntu-22.04, then inspected with readelf -d:

  • Built wheel: origami-0.1.0-cp310-cp310-linux_x86_64.whl — a per-version cp310-cp310 tag, not abi3. This corroborates the per-version ABI choice.
  • The extension's NEEDED entries: libamdhip64.so.7, libstdc++, libm, libgcc_s, libc, ld-linux — and no liborigami entry of any kind.

That absence is the static embed, confirmed by observation. It also defines the regression gate: a correct fix must flip this same output to include NEEDED liborigami.so.1. The reproduction script lives at .handoff/origami-py-phase2/readelf_experiment.sh.

Why this is the linchpin, not a footnote

The extension has NEEDED liborigami.so.1, so something must supply that library at import. Without the _dist_info.py entry, preload_libraries("origami") resolves no name and cannot load the SDK copy first; resolution then falls to the ordinary loader search path, which is not guaranteed to find the SDK's liborigami — import can fail, or a differently-sourced copy can win. The entry is what makes the SDK copy the one that loads, in order. It must land with or before the wheel.

8How we will know it works

The completion criteria are all observable checks, not judgments:

  • readelf -d on every shipped extension shows NEEDED liborigami.so.1 (satisfied by the find_package(origami) link, not a forced BUILD_SHARED_LIBS).
  • No shipped wheel contains a liborigami.so* file.
  • import origami succeeds on Python 3.10, 3.11, 3.12, and 3.13 against an installed SDK.
  • A single-copy regression test loads the SDK liborigami alongside the extension, round-trips a problem_t through select_config, and asserts exactly one liborigami.so.1 mapping in the process with no crash.
  • The reconciled rocm-origami release installs and imports across the consumer (PyTorch) CI matrix.

9Rollout and rollback

  1. Land the source changes in rocm-libraries, plus the TheRock workflow step and _dist_info.py entry; the Python-packages lane builds and import-tests all four wheels and runs the linker gate plus single-copy regression.
  2. Publish rocm-origami (reconciled version) to PyPI.
  3. Verify install and import across the consumer (PyTorch) CI Python matrix before touching the old releases.
  4. Yank predecessors (0.0.2, 0.0.1, 0.0.1.dev0) to close the window where the static-embed sdist can still be installed.
  5. Rollback path: if the release regresses, do not yank the predecessors; the fix is self-contained to the wheel, so reverting the four wheels restores prior behavior.

Sequencing note and open items

The two TheRock changes (section 7) — the workflow step and the _dist_info.py entry — must land with or before the wheel: the step is what builds it, and the entry is what makes the SDK copy resolve. Both are required changes, not loose ends.
